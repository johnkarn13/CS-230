# CS-230
Project Overview
The client for this project was The Gaming Room, a company looking to expand its existing Android game, Draw It or Lose It, into a web-based application that players could access from different devices and operating systems. The game involves teams guessing images as they are gradually revealed, with timed rounds and rules for how players and teams participate. The client needed a design that would preserve that gameplay while supporting multiple users, unique game and team names, consistent game sessions, and secure access across platforms.
What did you do particularly well in developing this documentation?
I think one of the stronger parts of my design document was looking at the entire system instead of treating each requirement as a separate problem. I compared Linux, Windows, macOS, and mobile environments, then connected those findings to a recommendation for a Java-based server running on Linux with players using a web browser. I also made sure to address security, memory and storage management, and the network issues that come with having multiple users connected at once. The goal was to explain not just what I recommended, but why it made sense for this client's needs.
What about the process of working through a design document did you find helpful when developing the code?
Working through the design document forced me to think about requirements and the overall structure before jumping into programming. Defining how games, teams, and players relate to one another made it easier to see where the classes and design patterns fit. For example, the Singleton pattern helped organize access to the game service, while the Iterator pattern provided a way to work through collections and check for duplicate names. It also helped me recognize that decisions that work in a small Java application may need additional support, such as database-level uniqueness, once the system runs across multiple servers.
If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?
I would spend more time on the distributed-system portion of the design. I addressed network communication, potential outages, and keeping game information consistent, but I would like to go further into how the application would recover when players disconnect or a server fails. I would improve that section by adding a clearer diagram of how the browser, application server, and database communicate, along with examples of reconnecting to a game and handling simultaneous requests. That would make the design easier for a development team to turn into a working application.
How did you interpret the user's needs and implement them into your software design? Why is it important to consider the user's needs when designing?
I started with what The Gaming Room wanted the software to accomplish: keep the existing rules of Draw It or Lose It while allowing people to play from more than just Android devices. From there, I translated those goals into technical requirements, including browser compatibility, a central source of game data, unique identifiers, secure communication, and support for multiple game sessions. This is important because a design can be technically impressive and still fail if it does not solve the client's problem. Understanding the user's needs helps keep development focused and prevents unnecessary features or costly redesigns later.
How did you approach designing software? What techniques or strategies would you use in the future to analyze and design a similar software application?
My approach was to break the problem down into requirements, constraints, platform options, and the individual components needed to make everything work together. I compared the strengths and weaknesses of different operating systems before recommending an architecture, instead of choosing a platform simply because I was familiar with it. Going forward, I would follow that same process while putting even more emphasis on diagrams, testing assumptions early, and considering scalability and failure scenarios from the beginning. This project helped me see that software design is more than getting code to run; it is making decisions that allow a program to remain reliable, maintainable, and useful as its requirements change.
